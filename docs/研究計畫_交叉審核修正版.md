## 0. 建議決策摘要

研究方向可行，但需把研究主張收斂成可量測的 HIL 時序與控制驗證。建議題目：

**具可重現時序量測之 STM32 四旋翼硬體迴路模擬平台：以 Unity 進行 3D 虛擬驗證**

建議採「自製 STM32 控制器」主線：一片 NUCLEO-G474RE 執行控制程式，第二片板子擷取實際 PWM；PC 執行固定步階的 6-DOF 植物模型及虛擬感測器；Unity 只顯示狀態快照。第一版不接 ESC、馬達或螺旋槳。

建議研究貢獻聚焦於：

1. Unity 渲染與固定步階模型分離後，HIL 更新率、延遲、抖動及逾時率的實測。
2. 以實體 PWM 腳位量測值驅動植物模型，與理想軟體 actuator 命令比較。
3. 同一模型下 SIL/HIL 的階躍響應、資料延遲、PWM 框架與感測誤差差異。
4. 公開可重播的參數、協定、韌體/模型版本和實驗紀錄。

**不可先宣稱「首創」「高擬真」或「1–2 ms 延遲已達成」。** 相關 STM32 HIL 已有先例；延遲必須先定義量測邊界並實測。[R01–R04]

## 1. 研究問題、目標與範圍

### 研究問題

- PC 植物模型、UART 感測注入、STM32 控制器及 PWM 擷取，能否在指定控制頻率下連續閉迴路運作？
- Unity 渲染負載對模型步階、HIL 延遲、抖動及逾時有多大影響？
- 加入馬達動態、IMU 雜訊、固定延遲、抖動與封包遺失後，PID 的超越量、整定時間及姿態 RMSE 如何改變？
- SIL 與 HIL 的差異可以由 PWM 更新、通訊、排程及感測誤差解釋到什麼程度？

### 研究目標

- 建立可重現的 6-DOF 四旋翼剛體及初階馬達模型。
- 建立 PC→STM32 虛擬感測器資料與 STM32 實體 PWM 輸出的閉迴路。
- 量測序列傳輸延遲、抖動、PWM 脈寬/週期、封包錯誤及逾時。
- 以姿態階躍、輸出飽和、陣風、感測噪聲及通訊故障進行 SIL/HIL 比較。
- 保存可重播的設定、程式版本與原始資料。

### 第一版不納入

- 不做螺旋槳飛行；不需先購買 ESC/馬達。
- 不同時移植 PX4、ArduPilot 和自製控制器。
- 不把 Unity 畫面 FPS 當作控制頻率。
- 不在沒有校準或對照資料時宣稱模型「高擬真」。
- 地面效應、GNSS、相機、實飛皆列為選配延伸。

## 2. 原計畫交叉審核與修正

| 原稿主張 | 判定 | 修正及依據 |
|---|---|---|
| HIL 可降低初期實飛風險 | 大方向正確，非零風險 | 先用無槳 bench 測試；HIL 仍須防輸出誤動作及錯誤接線。[R11] |
| Unity 同時負責 1 kHz 物理更新與渲染 | **錯誤假設** | Unity `FixedUpdate` 預設 0.02 秒（50 Hz），且一個畫面更新期間可能呼叫零次或多次。數值 HIL 時鐘須獨立，Unity 只讀快照。[R09–R10] |
| C# 多執行緒即可保證低延遲 | **不能保證** | 多執行緒可降低渲染阻塞，但 USB、OS 排程、GC、緩衝與裝置仍會產生抖動；需量測 p50/p95/p99/最大值及逾時率。桌面 OS 不可先宣稱硬即時。 |
| UART DMA 會把延遲控制在 1–2 ms | **尚無證據** | DMA 降低 MCU 搬運工作，不能消除線上傳輸、USB、PC 排程和同步等待。1 kHz 週期只有 1 ms；1–2 ms 往返會造成至少一個週期的資料延後，必須當作待研究變數。 |
| PWM 輸出等於 1 kHz actuator 更新 | **不正確** | 一般 PWM ESC frame rate 約 50–490 Hz，取決於輸出與 ESC；控制迴圈頻率、PWM 框架、感測器更新需分開量測。[R22–R23] |
| IMU 雜訊只需加高斯白雜訊與 random walk | **過於簡化** | 可作初階模型；噪聲密度與 bias 需依資料表/靜態紀錄估計。Kalibr 離散噪聲換算有取樣及低通/decimation 假設。[R24–R27] |
| Unity 視覺逼真代表動力學擬真 | **不成立** | 視覺呈現與模型有效性分開驗證；需做單位/座標檢查、懸停平衡、已知輸入及參數校準。[R05–R08] |
| PX4/ArduPilot 可直接接自訂 UART＋PWM | **不成立** | PX4 外部 Simulator MAVLink API 以 HIL_SENSOR 餵入感測值、HIL_ACTUATOR_CONTROLS 回傳模擬器；硬體 HIL 有輸出阻擋及特定 firmware 模組條件。不是自製 MCU 實體 PWM 測試路徑。[R11–R13] |
| ArduPilot JSON SITL 就等於硬體 HIL | **混淆兩條路徑** | JSON 是外部模擬器與 SITL 介面；Simulation on Hardware 是在特定飛控板上執行模擬功能，對板型與 firmware 有要求。官方目前只提供有限預編譯板型；不可假設任意 STM32 都可套用。[R14–R17] |
| STM32 + HIL 本身有研究新穎性 | **不足以支持** | 已有 STM32/Gazebo、Pixhawk HIL，並找到 2025 STM32/X-Plane 論文紀錄。研究缺口需由正式資料庫回顧後界定。[R01–R04] |
| 地面效應可用單旋翼係數直接套四旋翼 | **不可靠** | 轉子間距和多旋翼/地面的互相作用會改變流場，進階模型需要額外驗證。[R28–R29] |

### 延遲估算範例（不是實測）

UART 8N1 每 byte 約需 10 個線路 bit。單一 48-byte 封包在 921,600 baud 的理想傳輸時間為 `48 × 10 / 921600 ≈ 0.521 ms`。這未包含 USB/OS 等待、排隊、韌體處理、PWM 相位或握手時間。UART 全雙工時兩個方向可並行，應分方向量測並以邏輯分析儀/GPIO marker 驗證端到端時間。

### PC 與 Unity

- HIL Host 管理單調時鐘、序號、固定步階、timeout 和記錄。
- 植物模型與 UART I/O 不由 Unity `Update`/`FixedUpdate` 驅動。
- `Time.fixedDeltaTime` 只設定 Unity fixed-time 更新間隔，本身不會讓 PC/USB 成為即時系統。[R36]
- Unity 主執行緒只讀最新狀態快照、渲染模型和 HUD；API 不跨執行緒呼叫。
- 比較渲染開啟/關閉時模型步階 deadline miss。若有影響，改成 headless 模型程序＋Unity viewer。
- Windows/USB 原型可量測，但不能先宣稱硬即時。

### STM32 控制器與 PWM 擷取

- 建議 NUCLEO-G474RE 執行自製控制器；官方列出 STM32G474RE 170 MHz Cortex-M4/FPU、最高 512 KB Flash、128 KB SRAM。這是開發板選擇，不代表可直接執行 PX4/ArduPilot 堆疊。[R19–R20]
- 使用 STM32CubeIDE/CubeMX、HAL/LL、UART DMA、timer PWM。HIL 虛擬 IMU 會取代實體 IMU 輸入，因此不能宣稱已驗證實體 IMU driver/震動。
- 第二片相容 Nucleo 用 timer input capture 量 PWM 寬度和週期，回傳 PC。使用共地、核對 3.3 V I/O 與 pin mapping；以邏輯分析儀交叉檢查。
- 第一版只量標準 PWM。DShot 是不同數位協定，不能沿用 PWM pulse capture。[R22–R23]

### 封包建議

自製控制器採最小固定格式：同步標記、版本、類型、序號、單調時間戳、長度、payload、CRC-16。固定端序及單位；不要直接傳 C/C++ 記憶體結構，以免 padding/ABI 不同。

- PC→MCU：三軸加速度 m/s²、三軸角速度 rad/s、選配壓力、時間戳、狀態旗標。
- PWM 擷取板→PC：四路 pulse width µs、週期 µs、捕獲時間、序號及狀態。
- CRC 錯誤、封包過期、跳號或連線中斷時拒收資料、執行定義好的安全狀態並留 log。
- 若改走 PX4/ArduPilot，遵循其官方 MAVLink/simulator protocol，不再設計平行的自訂格式。[R12–R17]

## 5. 植物與感測器模型

### 座標及單位

模型內部建議 NED 世界座標、FRD 機體座標、SI 單位及弧度；Unity 為左手座標系，X 右、Y 上、Z 前。只在狀態輸出到 Unity 時轉換，並用單軸向量測試驗證符號。[R12, R18]

令 `R_bn` 將 FRD 向量轉到 NED，`p_n, v_n` 為位置/速度，`ω_b` 為機體角速度：

- `ṗ_n = v_n`
- `v̇_n = g_n + R_bn f_b / m`
- `Ṙ_bn = R_bn [ω_b]×`
- `J ω̇_b = τ_b − ω_b × (J ω_b) − D_ω ω_b`

NED 重力 `g_n=[0,0,g]`，機體推力沿 FRD 負 z 軸。程式符號以座標測試為準，不只複製公式。

四旋翼初階模型：

- `T_i = k_f Ω_i²`
- `Q_i = s_i k_m Ω_i²`
- `τ_m Ω̇_i + Ω_i = Ω_cmd,i`
- `Ω_cmd,i = f(PWM_i)`，映射需識別或明確設成假設；PWM pulse width 不是推力。

參數至少需有質量、慣量、臂長、推力/反扭矩係數、阻尼、馬達時間常數。四旋翼建模/參數識別文獻把這些列為核心項目；馬達延遲也是有研究的識別對象。[R05–R06, R21, R34–R35]

### 感測器模型

- Gyro：`ω_meas = ω_b + b_g + n_g`
- Accelerometer：`f_meas = R_bnᵀ(v̇_n − g_n) + b_a + n_a`
- 初版先用可校準白雜訊及慢變 bias；noise density 依資料表/靜態紀錄，bias random walk 可由 Allan deviation 估計。
- Kalibr 離散白雜訊縮放假設特定取樣和理想低通/decimation；單純降採樣時不可直接套用。[R24–R27]
- 若 MCU 收高度而非壓力，文件需標明這不是氣壓感測器完整 pipeline。

### 擬真度分階

| 等級 | 模型內容 | 驗證 |
|---|---|---|
| L0 | 重力、質量、四路推力/力矩、姿態/位置 | 單位、重力落體、懸停平衡、單軸正負 |
| L1 | 馬達一階延遲、推力映射、輸出限幅、PWM 量化 | 馬達階躍、推力台或已知模型比較 |
| L2 | 阻力、陣風、IMU 白雜訊/bias、延遲/丟包 | 固定 seed 重播，報告統計 |
| L3（選配） | 地面效應、轉子互擾、電池、氣壓/磁/GNSS/相機 | 需額外資料及校準，不靠視覺效果驗證 |

單旋翼地面效應係數不能直接視作四旋翼完整模型；多旋翼流場受轉子間距與地面交互影響。[R28–R29]

## 8. 實驗指標與順序

### 系統指標

- 更新率和 deadline miss；單向/往返延遲 p50/p95/p99/最大值、樣本數和量測期間。
- jitter、sensor 資料齡期、封包遺失/CRC/跳號/timeout。
- 四路 PWM pulse width、週期、更新率、抖動、飽和比例。
- MCU CPU/ISR/stack，host CPU/GC/渲染 FPS。
- 斷線至安全狀態的時間，及錯誤封包後是否拒收過期資料。

### 控制指標與流程

姿態 step 的超越量、上升/整定時間、穩態誤差、RMSE/IAE；相同初始條件/seed/參數比較 SIL/HIL。延遲、抖動、單包/連續丟包逐項掃描；噪聲參數從資料表或校準估計。保存原始資料，不能以單次 demo 當結論。

1. UART DMA 壓力測試、CRC/序號/timeout。
2. 一板輸出固定 PWM、另一板擷取，並以邏輯分析儀交叉比對。
3. 開迴路植物驗證重力、方向、限幅與馬達延遲。
4. PC SIL 閉迴路調整單一 baseline PID。
5. 無槳 HIL 閉迴路、姿態階躍。
6. 延遲/抖動/遺失故障注入及 failsafe。
7. 估計 IMU noise 與陣風情境。
8. 可選推力台校準或實飛資料比較；不是完成核心論文的先決條件。

## 11. 風險與處理

| 風險 | 因應 |
|---|---|
| Windows/USB jitter 過大 | M3–4 先測；分離渲染、縮短封包、調整頻率，必要時比較 Linux/即時目標。 |
| PWM frame 等待造成舊資料 | 實測週期/相位，把輸出等待納入總延遲。 |
| CRC/timeout 後沿用舊值 | 序號、時間戳、CRC、watchdog、安全狀態及記錄。 |
| NED/FRD/Unity 座標混亂 | 固定 frame；做重力、單軸及懸停測試，只在 Unity 邊界轉換。 |
| 缺少真實參數 | 公開假設與敏感度；可選推力台/慣量估計；限制論文結論。 |
| 舊 Unity 專案不相容 | Flightmare/AirSim 作參考，不作前置依賴；鎖定 Unity 版先做建置可行性。 |
| 新穎性重疊 | 先完成正式資料庫回顧，再把貢獻限於 PWM 實體擷取、render-load timing study 和可重現評估。 |
| 範圍擴大 | 第一版限 attitude plant、IMU、PWM、時序；vision/GNSS/飛行列選配。 |

## 14. 結論與需確認之處

本題可做，但原稿需把「Unity 模擬、UART、STM32 PWM」改成有固定時鐘、座標、實體輸出擷取、延遲量測及模型校準依據的閉迴路平台。第一個關鍵工作應是 M3–4 UART/PWM 時序實驗，而非先完成 3D 場景。

最合適的主軸是自製 STM32 控制器＋實體 PWM 擷取，Unity 作旁觀者視覺化；若研究對象是 PX4/ArduPilot 原廠韌體，應改採官方 HIL 介面並重訂研究問題。正式提案前需取得 [R01]、[R04] 全文/正式 metadata，完成資料庫檢索後才能定案新穎性。
