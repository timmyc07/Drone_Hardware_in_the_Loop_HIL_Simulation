## 0. 建議決策摘要

研究方向可行，但需把研究主張收斂成可量測的 HIL 時序與控制驗證。建議題目：

**具可重現時序量測之 STM32 四旋翼硬體迴路模擬平台：以 Unity 進行 3D 虛擬驗證**

建議採「自製 STM32 控制器」主線：一片 NUCLEO-G474RE 執行控制程式，第二片板子以 timer input capture 擷取實際 PWM；PC 執行有獨立時鐘的 6-DOF 植物模型及虛擬感測器；Unity 只顯示狀態快照。第一版不接 ESC、馬達或螺旋槳。這條路線驗證的是控制演算法、UART 輸入及 PWM 輸出；它**不會**驗證實體 IMU 的 SPI/I²C driver。

建議研究貢獻聚焦於：

1. Unity 渲染開/關對固定步階模型 deadline miss、閉迴路週期及延遲分布的影響。
2. 以實體 PWM 腳位擷取值驅動植物模型，量出 waveform-level I/O 與只傳軟體 actuator 命令的差異。
3. 同一模型下 SIL/HIL 的階躍響應、資料延遲、PWM 框架與感測誤差差異。
4. 公開可重播的參數、協定、韌體/模型版本和實驗紀錄。

**不可先宣稱「首創」「高擬真」或「1–2 ms 延遲已達成」。** 已核對到 2018 STM32F4/Gazebo HIL 與 2025 STM32F4/X-Plane/Python HIL；另有 2021 HIL 平台在 100 Hz 測得平均 6 ms、最大 9 ms。它們不是你的硬體/協定直接基準，但足以說明 1–2 ms 不是可直接假設的預設值。[R01–R04, R39]

## 1. 研究問題、目標與範圍

### 研究問題

- PC 植物模型、UART 感測注入、STM32 控制器及 PWM 擷取，能否在指定控制頻率下連續閉迴路運作？
- Unity 渲染負載對模型步階、HIL 延遲、抖動及逾時有多大影響？
- 加入馬達動態、IMU 雜訊、固定延遲、抖動與封包遺失後，PID 的超越量、整定時間及姿態 RMSE 如何改變？
- SIL 與 HIL 的差異可以由 PWM 更新、通訊、排程及感測誤差解釋到什麼程度？

### 研究目標

- 建立可重現的 6-DOF 四旋翼剛體及初階馬達模型。
- 建立 PC→STM32 虛擬感測器資料與 STM32 實體 PWM 輸出的閉迴路。
- 量測序列傳輸延遲、抖動、PWM 脈寬/週期、封包錯誤及逾時。
- 以姿態階躍、輸出飽和、陣風、感測噪聲及通訊故障進行 SIL/HIL 比較。
- 保存可重播的設定、程式版本與原始資料。

### 第一版不納入

- 不做螺旋槳飛行；不需先購買 ESC/馬達。
- 不同時移植 PX4、ArduPilot 和自製控制器。
- 不把 Unity 畫面 FPS 當作控制頻率。
- 不在沒有校準或對照資料時宣稱模型「高擬真」。
- 地面效應、GNSS、相機、實飛皆列為選配延伸。

## 2. 原計畫交叉審核與修正

| 原稿主張 | 判定 | 修正及依據 |
|---|---|---|
| HIL 可降低初期實飛風險 | 大方向正確，非零風險 | 先用無槳 bench 測試；HIL 仍須防輸出誤動作及錯誤接線。[R11] |
| Unity 同時負責 1 kHz 物理更新與渲染 | **錯誤假設** | Unity `FixedUpdate` 預設 0.02 秒（50 Hz），且一個畫面更新期間可能呼叫零次或多次。數值 HIL 時鐘須獨立，Unity 只讀快照。[R09–R10] |
| C# 多執行緒即可保證低延遲 | **不能保證** | 多執行緒可降低渲染阻塞，但 USB、OS 排程、GC、緩衝與裝置仍會產生抖動；需量測 p50/p95/p99/最大值及逾時率。桌面 OS 不可先宣稱硬即時。 |
| UART DMA 會把延遲控制在 1–2 ms | **錯誤推論** | DMA 只降低 MCU 搬運工作，不會消除線上傳輸、USB、OS 排程、PWM 相位等待及跨時鐘同步誤差。相關 HIL 研究報告約 6 ms 平均/9 ms 最大延遲或 12–13 ms 請求週期；量測方法不同，不能直接排名，但 1–2 ms 不應作先驗門檻。[R01, R39] |
| 1 kHz 控制迴圈等於 1 kHz HIL/PWM 閉迴路 | **混為一談** | MCU 內部控制、感測器注入、PWM 訊號框架與主機植物更新可有不同頻率。傳統 PWM 的輸出更新被 frame rate/相位限制；DShot 等數位協定是另一條 I/O 路徑。第一版先選定並量測 PWM frame，不能把 1 kHz 寫成整體 HIL 已達標。[R22–R23, R39] |
| IMU 雜訊只需加高斯白雜訊與 random walk | **過於簡化** | 可作初階模型；噪聲密度與 bias 需依資料表/靜態紀錄估計。Kalibr 離散噪聲換算有取樣及低通/decimation 假設。[R24–R27] |
| Unity 視覺逼真代表動力學擬真 | **不成立** | 視覺呈現與模型有效性分開驗證；需做單位/座標檢查、懸停平衡、已知輸入及參數校準。[R05–R08] |
| PX4/ArduPilot 可直接接自訂 UART＋PWM | **不成立** | PX4 外部 HITL 使用 MAVLink HIL sensor/actuator path 和相容 firmware；官方現行文件標示 HITL 為 community supported。SIH 則是在 autopilot 硬體內執行 plant 的另一條路徑。兩者都不是自製 STM32 controller + 實體 PWM 擷取的同一實驗。[R11–R13, R47] |
| ArduPilot JSON SITL 就等於硬體 HIL | **混淆兩條路徑** | JSON 是外部模擬器與 SITL 介面；Simulation on Hardware 是在特定飛控板上執行模擬功能，對板型與 firmware 有要求。官方目前只提供有限預編譯板型；不可假設任意 STM32 都可套用。[R14–R17] |
| STM32 + HIL 本身有研究新穎性 | **已被先前工作直接重疊** | `[R01]` 早在 2018 年已用 STM32F4、Gazebo、serial protocol 和 DLQR；`[R04]` 2025 年又有 STM32F4、X-Plane 12、Python middleware 的 HIL 平台。可研究的差異需縮到實體 PWM 擷取、渲染負載的時序影響、可重現 benchmark 等，並待取得 `[R04]` 全文後重新判定。[R01, R04] |
| 六軸 IMU 可校正所有姿態角（包含絕對 yaw） | **不成立** | 加速度計主要提供重力方向，gyro 積分有 bias drift；若沒有 magnetometer、GNSS/vision heading 等外部參考，絕對 yaw 不可觀測。只測 roll/pitch 或相對 yaw rate，或把磁力計納入虛擬感測器並評估磁干擾。[R24–R27, R41] |
| 地面效應可用單旋翼係數直接套四旋翼 | **不可靠** | 轉子間距和多旋翼/地面的互相作用會改變流場，進階模型需要額外驗證。[R28–R29] |

### 延遲估算範例（不是實測）

UART 8N1 每 byte 約需 10 個線路 bit。單一 48-byte 封包在 921,600 baud 的理想傳輸時間為 `48 × 10 / 921600 ≈ 0.521 ms`。這未包含 USB/OS 等待、排隊、韌體處理、PWM 相位或握手時間。UART 全雙工時兩個方向可並行，應分方向量測並以邏輯分析儀/GPIO marker 驗證端到端時間。

- 2018 IFAC 論文研究 Pixhawk、PID 與三自由度測試台；說明多旋翼 HIL 已有成熟先例。[R02]
- 2022 開放論文提出四旋翼模型與 Pixhawk/Mission Planner HIL。[R03]
- 2025 IEEE CiST 會議目錄確認 `[R04]` 題名、作者與發表紀錄；DOI `10.1109/CIST65886.2025.11224143` 的索引摘要描述 STM32F4、X-Plane 12、Python middleware、感測器模擬及 actuator command translation。IEEE Xplore 網頁要求 JavaScript/反機器人驗證，公開作者全文未找到；故已完成可得 metadata/摘要核對，但全文實驗細節仍未核實，不引用其 latency 數值。
- 2021 開放 HIL 示範研究在 100 Hz sample rate，記錄平均 6 ms、最大 9 ms 的 latency，並分解了模擬、通訊及 Pixhawk 計算。它不是本計畫所用 MCU/協定的同條件比較，但提供可查驗的量級參照。[R39]
- 2026 Scientific Reports 研究以 STM32/ArduCopter/Mission Planner HIL 評估失控偵測，主題是安全演算法而非 Unity 植物模型平台。[R30]

### 須避免的主張

不要稱「第一套 STM32 HIL」「首創 Unity 飛控驗證」「高擬真」或「延遲低於 2 ms」。較可辯護的暫定研究問題是：**實體 PWM 波形擷取與 Unity 渲染開/關，分別如何影響 HIL 閉迴路時序與 attitude tracking 指標？** 只有在取得 `[R04]` 全文、完成正式資料庫回顧並確認先前研究未做同一對照後，才把它寫成研究缺口。

### 暫定假設

相同模型與控制參數下，採用實體 PWM 輸出擷取、感測器誤差及可控通訊延遲後，HIL 階躍響應會與理想 SIL 出現可測差異；差異可由更新週期、延遲與感測誤差解釋。此為待驗假設，非預設結論。

### PC 與 Unity

- HIL Host 管理單調時鐘、序號、固定步階、timeout 和記錄。
- 植物模型與 UART I/O 不由 Unity `Update`/`FixedUpdate` 驅動。
- `Time.fixedDeltaTime` 只設定 Unity fixed-time 更新間隔，本身不會讓 PC/USB 成為即時系統。[R36]
- Unity 主執行緒只讀最新狀態快照、渲染模型和 HUD；API 不跨執行緒呼叫。
- 比較渲染開啟/關閉時模型步階 deadline miss。若有影響，改成 headless 模型程序＋Unity viewer。
- Windows/USB 原型可量測，但不能先宣稱硬即時。

### STM32 控制器與 PWM 擷取

- 建議 NUCLEO-G474RE 執行自製控制器；官方列出 STM32G474RE 170 MHz Cortex-M4/FPU、最高 512 KB Flash、128 KB SRAM。這是開發板選擇，不代表可直接執行 PX4/ArduPilot 堆疊。[R19–R20]
- 使用 STM32CubeIDE/CubeMX、HAL/LL、UART DMA、timer PWM。HIL 虛擬 IMU 會取代實體 IMU 輸入，因此不能宣稱已驗證實體 IMU driver/震動。
- 第二片相容 Nucleo 用 timer input capture 量 PWM 寬度和週期，回傳 PC。使用共地、核對 3.3 V I/O 與 pin mapping；以邏輯分析儀交叉檢查。
- 第一版只量標準 PWM。DShot 是不同數位協定，不能沿用 PWM pulse capture。[R22–R23]

### 封包建議

自製控制器先以 MAVLink 2 `HIL_SENSOR` 接收虛擬感測資料；PWM capture board→PC 則定義一個語意明確的 MAVLink dialect 擴充訊息（例如 `PWM_CAPTURE`）傳回**實際量測**的脈寬、週期、捕獲時間與通道狀態。沿用 MAVLink framing/CRC/sequence 與生成的 C library，不另造通用封包層。`SERVO_OUTPUT_RAW` 表示 servo output 值，不完整表示 waveform 捕獲細節；`HIL_ACTUATOR_CONTROLS` 更是軟體 actuator command，兩者都不直接當作實體 PWM capture record。[R12–R13, R43]

- PC→MCU：`HIL_SENSOR` 的三軸加速度 m/s²、角速度 rad/s、若納入則有磁場/壓力/溫度，以及 `time_usec`/fields-updated flags。
- PWM 擷取板→PC：MAVLink dialect 擴充訊息 `PWM_CAPTURE` 回報四路 pulse width µs、timer-measured period、rising-edge capture timestamp 及漏脈衝/狀態旗標；實際通道/端口映射列入版本化設定。
- CRC 錯誤、封包過期、timeout 或 PWM 輸出停止時，拒收過期感測值、停用/置安全輸出並留 log；只接無槳 bench，不接 ESC。
- 只有 MAVLink 實測吞吐/時序不符需求時，才以小型 COBS+CRC frame 取代，並與 MAVLink baseline 做同條件 benchmark。[R12–R13, R43]

`PWM_CAPTURE` 最小欄位草案：`time_usec[4]`（capture MCU 單調時鐘、各 channel rising edge）、`pulse_width_us[4]`、`period_us[4]`、`valid_mask` 和 `capture_status`；MAVLink header 提供 sequence/CRC。Capture board 必須先以 timer input capture 在 MCU 上量出寬度/週期，再傳資料；四路時戳不與 PC QPC 直接相減，除非另做 offset/drift 同步校準。

## 5. 植物與感測器模型

### 座標及單位

模型內部建議 NED 世界座標、FRD 機體座標、SI 單位及弧度；Unity 為左手座標系，X 右、Y 上、Z 前。只在狀態輸出到 Unity 時轉換，並用單軸向量測試驗證符號。[R12, R18]

令 `R_bn` 將 FRD 向量轉到 NED，`p_n, v_n` 為位置/速度，`ω_b` 為機體角速度：

- `ṗ_n = v_n`
- `v̇_n = g_n + R_bn f_b / m`
- `Ṙ_bn = R_bn [ω_b]×`
- `J ω̇_b = τ_b − ω_b × (J ω_b) − D_ω ω_b`

NED 重力 `g_n=[0,0,g]`，機體推力沿 FRD 負 z 軸。程式符號以座標測試為準，不只複製公式。

四旋翼初階模型：

- `T_i = k_f Ω_i²`
- `Q_i = s_i k_m Ω_i²`
- `τ_m Ω̇_i + Ω_i = Ω_cmd,i`
- `Ω_cmd,i = f(PWM_i)`，映射需識別或明確設成假設；PWM pulse width 不是推力。

參數至少需有質量、慣量、臂長、推力/反扭矩係數、阻尼、馬達時間常數。四旋翼建模/參數識別文獻把這些列為核心項目；馬達延遲也是有研究的識別對象。[R05–R06, R21, R34–R35]

### 感測器模型

- Gyro：`ω_meas = ω_b + b_g + n_g`
- Accelerometer：`f_meas = R_bnᵀ(v̇_n − g_n) + b_a + n_a`
- 初版先用可校準白雜訊及慢變 bias；noise density 依資料表/靜態紀錄，bias random walk 可由 Allan deviation 估計。
- Kalibr 離散白雜訊縮放假設特定取樣和理想低通/decimation；單純降採樣時不可直接套用。[R24–R27]
- 若 MCU 收高度而非壓力，文件需標明這不是氣壓感測器完整 pipeline。

### 擬真度分階

| 等級 | 模型內容 | 驗證 |
|---|---|---|
| L0 | 重力、質量、四路推力/力矩、姿態/位置 | 單位、重力落體、懸停平衡、單軸正負 |
| L1 | 馬達一階延遲、推力映射、輸出限幅、PWM 量化 | 馬達階躍、推力台或已知模型比較 |
| L2 | 阻力、陣風、IMU 白雜訊/bias、延遲/丟包 | 固定 seed 重播，報告統計 |
| L3（選配） | 地面效應、轉子互擾、電池、氣壓/磁/GNSS/相機 | 需額外資料及校準，不靠視覺效果驗證 |

單旋翼地面效應係數不能直接視作四旋翼完整模型；多旋翼流場受轉子間距與地面交互影響。[R28–R29]

### 11.1 時序邊界與量測方法

將「延遲」拆成四個量，避免一個數字混用：

1. **線路延遲：** 邏輯分析儀量 UART frame 開始/結束、MCU PWM edge；`Nbyte × 10 / baud` 只是 8N1 理想線速下限。
2. **控制器反應：** UART sensor frame 結束到 MCU PWM compare 更新/實際輸出 edge；用 PWM capture timer 或 MCU GPIO marker 定位。
3. **閉迴路 host cycle：** host sensor send timestamp 到收到 capture board 回報；使用主機同一個 monotonic clock 算 p50/p95/p99/max，另記 deadline miss、timeout、sample age。
4. **跨時鐘誤差：** MCU timer、capture board timer、PC QPC 起始值未同步，不能直接相減。先用共同 logic analyzer/marker 測 wire interval；若要融合多時鐘資料，額外估 offset/drift 並報校準誤差。

**頻率試驗先走 100 Hz 功能基線，再掃描 250 Hz、實際 PWM frame 上限與更高檔位。** 每檔至少做 UART-only、PWM capture-only、閉迴路、render-on/off、滿載與斷線故障測試。沒有測得資料前不設 `1–2 ms` 通過門檻。若控制演算法本身跑 500 Hz/1 kHz，也要將 MCU loop rate 單獨記錄，不能宣稱整體 sensor→PWM HIL loop 同頻。[R01, R39, R45–R47]

### 11.2 開工前的路線凍結

- **自製 STM32 firmware（本文件主線）：** 虛擬感測器從 UART 注入，MCU 執行 estimator/controller，實體 PWM 由第二片板量測。限制：沒有驗證實體 sensor driver 或原廠 PX4/ArduPilot 整合。
- **PX4/ArduPilot 原廠 firmware：** 改用其 HIL/SIH/JSON/MAVLink 支援與相容硬體；不應假設任意 STM32G4 板可執行完整 autopilot。PX4 文件標示外部 HITL 受 community support，SIH on hardware 是不同架構。[R11–R17]
- **實體 sensor driver 測試：** 加實體 sensor 或 SPI/I²C bus emulator，另訂電氣 timing 與應答 fidelity；不屬於現有 UART 版本的低成本核心範圍。

因此第 1 個月需由指導教授確認「研究對象是自製 estimator/controller，還是 PX4/ArduPilot flight stack」。確認後刪掉未採路線的方案，避免一篇碩論同時重做三套飛控堆疊。

## 12. 風險與處理

| 風險 | 因應 |
|---|---|
| Windows/USB jitter 過大 | M3–4 先測；分離渲染、減少封包、調整更新率，必要時用 Linux PREEMPT_RT/real-time target 對照。 |
| lockstep 掩蓋 deadline miss | 同時跑 lockstep 與 wall-clock paced；以後者報 real-time deadline 結果。 |
| PWM frame 等待造成舊資料 | 實測週期/相位，把輸出更新等待納入 sensor→PWM latency。 |
| CRC/timeout 後沿用舊值 | 序號、時間戳、CRC、watchdog、安全狀態及記錄。 |
| NED/FRD/Unity 座標混亂 | 固定 frame；做重力、單軸及懸停測試，只在 Unity 邊界轉換。 |
| 缺少真實參數 | 公開假設與敏感度；可選推力台/慣量估計；限制論文結論。 |
| 舊 Unity 專案不相容 | Flightmare/AirSim 作參考，不作前置依賴；鎖定 Unity 版先做建置可行性。 |
| 新穎性重疊 | 先完成正式資料庫回顧，再把貢獻限於 PWM 實體擷取、render-load timing study 和可重現評估。 |
| 範圍擴大 | 第一版限 attitude plant、IMU、PWM、時序；vision/GNSS/飛行列選配。 |

## 15. 結論與需確認之處

本題可做，但原稿需把「Unity 模擬、UART、STM32 PWM」改成有固定時鐘、座標、實體輸出擷取、延遲量測及模型校準依據的閉迴路平台。第一個關鍵工作應是 M3–4 UART/PWM 時序實驗，而非先完成 3D 場景。

最合適的主軸是自製 STM32 控制器＋實體 PWM 擷取，Unity 作旁觀者視覺化；若研究對象是 PX4/ArduPilot 原廠韌體，應改採官方 HIL 介面並重訂研究問題。`[R01]` 公開全文與會議典藏已完成交叉核對，但原典藏和 OJS 重複紀錄的 DOI metadata 衝突尚未釐清；`[R04]` 已核對可見 metadata/摘要，仍須由圖書館或 IEEE 存取取得全文。新穎性最終判定及 Scopus/Web of Science/IEEE Xplore 可重現檢索筆數仍待校內資料庫存取，不能在本稿宣稱已完成系統性回顧。
